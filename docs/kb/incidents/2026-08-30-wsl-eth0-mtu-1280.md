# 2026-08-30 - eth0 came up at MTU 1280 and strangled the tunnel

**Fix: `sudo ip link set dev eth0 mtu 1500`, made permanent by the
`wsl-fix-mtu.service` systemd unit. Nothing on Windows was changed, and nothing
on Windows needs to be.**

This is the **same black-hole as [2026-08-08](2026-08-08-wsl-node-large-packet-blackhole.md)**,
but that one was healed by restarting tailscaled and the cause was left as "a
stale WinNAT mapping". That was wrong, or at least incomplete. The real cause is
a byte budget, and it is visible in one command.

## Symptom

From the PC (and any tailnet client), against `100.117.176.85`:

| probe | result |
|---|---|
| `tailscale ping` / `--tsmp` | pong in 1-2 ms - **all green** |
| `curl http://100.117.176.85/` | **`code=200 bytes=0`**, stalls until `-m` kills it |
| `curl http://100.117.176.85:8090/...` (Keycloak) | **`code=000`** - never answers |
| `curl http://192.168.107.43/` (LAN path) | `200`, 4682 bytes, **1.8 ms** |
| everything on `127.0.0.1` on the box | instant and complete |

So: the box was **entirely healthy**, every container up, every port listening.
Only the tunnel was broken, and only for packets over ~1200 bytes.

## Cause - the byte budget

```
eth0        MTU 1280   <-- the problem
tailscale0  MTU 1280   <-- Tailscale's fixed default
```

A full-size tunnel packet is 1280 bytes of payload **plus** WireGuard's
encapsulation - ~32 B WireGuard + 8 B UDP + 20 B IP = **~1340 bytes** on the
wire. eth0 could carry 1280. So every full-size packet was dropped on the way
out, with no ICMP to say so. That is a black hole, not an error:

- a small request (`tailscale ping`, a TLS ClientHello, an HTTP request line)
  fits, so the connection **opens and looks healthy**;
- the response body arrives in MSS-sized segments, which do **not** fit, so the
  body never lands. Hence `200` with `bytes=0`.

Measured hole, matching 08-08 almost exactly (`ping -M do -s N`):

```
payload 1180  OK          <-- 1180 + 28 + 60 = 1268, fits under 1280
payload 1200  DROP        <-- 1200 + 28 + 60 = 1288, does not
```

Keycloak was hit hardest because it never sends anything small: its
`.well-known` document, its login page and its admin-console bundle are all well
past one segment, so it failed outright rather than half-loading.

## Why eth0 was 1280 - and why Windows is NOT the fix

WSL2 brings eth0 up with the **smallest MTU it sees among the Windows host's
adapters**. On this host (read-only, `netsh interface ipv4 show subinterfaces`):

```
1280   Tailscale                            <-- Tailscale's own adapter
1500   Ethernet                             <-- carries the default route
1500   vEthernet (WSL (Hyper-V firewall))   <-- carries eth0's traffic
```

Windows' Tailscale adapter is 1280 (normal for Tailscale). WSL copied that
floor onto eth0 - even though eth0's traffic never touches that adapter; it goes
over the WSL vSwitch, which is 1500. So the constraint was **inherited, not
real**, which is exactly why the guest can simply override it.

This is why the box broke "after the Windows networking was fixed": that work
brought the Windows Tailscale adapter back up, WSL restarted, and eth0 inherited
1280 at boot. **No Windows setting is wrong and none was changed to fix this.**

## The fix

`/usr/local/sbin/wsl-fix-mtu` + `wsl-fix-mtu.service` (enabled, `multi-user.target`,
`Before=tailscaled.service`). It sets eth0 to 1500 and re-checks once after 10 s,
because WSL can re-apply the host-derived value shortly after boot. If eth0 ever
genuinely cannot take 1500, it falls back to shrinking **tailscale0 to 1180** so
encapsulated packets fit inside whatever eth0 has.

Verified by re-creating the fault: `ip link set eth0 mtu 1280` → 1252-byte tunnel
ping DROPs → `systemctl restart wsl-fix-mtu` → eth0 1500, same ping OK, and every
published service returns full bodies from the Windows client in single-digit ms
(portal 4682 B, Grafana 60126 B, Keycloak 3829 B).

## Ruled out

- **The box, the stack, Keycloak.** All healthy throughout, on loopback and on
  the LAN IP. Keycloak's `KC_HOSTNAME=http://100.117.176.85:8090` is correct.
- **DNS.** Nothing here resolves a name; it is all bare IP.
- **Traefik / routing.** The LAN path used the identical routers and was perfect.
- **Restarting tailscaled** - what "fixed" 08-08. It cannot fix this: tailscaled
  sets tailscale0 back to its fixed 1280, and eth0 stays 1280. If 08-08 recurs,
  **check `ip link show eth0` before restarting anything.**
- **Any Windows change** - MTU, portproxy, firewall, adapter metrics. Not needed.

## The rule this earns

> **`tailscale ping` proves reachability, never usable bandwidth.** Alongside
> "a 200 proves nothing about routing", add: **a 200 with `bytes=0` is an MTU
> black hole until proven otherwise.** Always curl with `%{size_download}`, and
> when it stalls, compare `ip link show eth0` against `ip link show tailscale0` -
> the underlay must exceed the tunnel by ~60 bytes, or large packets vanish.
